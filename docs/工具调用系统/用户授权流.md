# 用户授权流 (User Approval Flow)

为了平衡 AI 的自动化能力与系统的安全性，Open Zen 实现了一套可交互的工具授权机制。

## 核心流程

1.  **中断决策 (Backend)**:
    - 后端检测到 `tool_call` 请求调用的方法被标记为非免授权工具（`bypassUserApproval = false`）。
    - 若当前为“需要用户授权”模式，后端会保存带 `tool_calls` 的 assistant 消息，并通过 SSE `done` 事件中的 `toolApprovalRequired = true` 告知前端当前轮次暂停。
2.  **前端交互 (Frontend)**:
    - 前端 `ChatPage.tsx` 在刷新消息后，将该条 assistant 消息中的 `tool_calls` 渲染为“待授权”卡片。
    - **用户动作**: 用户点击“允许”或“拒绝”。
3.  **授权恢复 (Recovery)**:
    - **普通聊天**:
      - 流式续跑接口：`POST /api/chat/sessions/{sessionId}/tool-approval/stream`
      - 兼容同步接口：`POST /api/chat/sessions/{sessionId}/tool-approval`
    - **项目聊天**:
      - 流式续跑接口：`POST /api/projects/{projectId}/chat/sessions/{sessionId}/tool-approval/stream`
      - 兼容同步接口：`POST /api/projects/{projectId}/chat/sessions/{sessionId}/tool-approval`
    - 后端接收到确认指令后，会重新进入 `ChatService.runCompletionWithTools(...)` 闭环。
    - **允许**:
      - 先写入一条 `tool` 消息占位（内容为“工具执行中…”），避免刷新后仍停留在“允许/拒绝”状态。
      - 工具执行完成后回写最终 `tool` 结果，再把 `tool` 结果作为上下文继续提交给模型。
      - 普通聊天与项目聊天现在都会继续走 SSE，把后续 assistant 正文按增量输出给前端。
    - **拒绝**:
      - 后端写入“用户拒绝执行工具”对应的 `tool` 消息，再继续向模型请求后续回复。

## 消息聚合逻辑 (前端)

在 React 渲染层，为了避免“碎石化”的消息展示，`buildDisplayMessages` 函数会执行逻辑聚合：

- 它会将紧随在 `assistant` 消息后的多条 `tool` 角色消息（即工具执行结果）合并到同一个 `assistant` 消息卡片中展示。
- 每个工具调用在卡片中以单独的“步骤”显示其入参、状态（Pending/Running/Success/Failed）以及输出结果。

## 关键文件路径

- **前端授权动作**: `web/src/store/chatStore.ts` (方法: `resolveToolApproval`)
- **待授权卡片逻辑**: `web/src/pages/ChatPage.tsx` (`buildDisplayMessages` 与 `MessageCard`)
- **普通聊天授权 API**: `server/src/main/java/com/aiagent/controller/ChatController.java`
- **项目聊天授权 API**: `server/src/main/java/com/aiagent/controller/ProjectChatController.java`
- **后端执行拦截**: `server/src/main/java/com/aiagent/service/ChatService.java`
